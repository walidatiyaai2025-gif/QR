# DA Secure — IIS Deployment / Update / Rollback Package

This package deploys the `SecureQrPortal` ASP.NET Core application to the approved DA Secure IIS target without changing application business logic.

## Fixed production target defaults

- Deployment path: `C:\inetpub\wwwroot\QR`
- IIS Site: `API`
- IIS Application Pool: `QR`
- HTTPS host: `testapi.da.gov.kw`
- Certificate selector: `*.da.gov.kw`
- Deployment backup root: `C:\inetpub\wwwroot\QR_deployment_backups`
- Health endpoint: `https://testapi.da.gov.kw/health`
- Target framework: `.NET 10 / net10.0`

All scripts require an elevated Windows PowerShell session. The installer is idempotent for the site/application-pool target and can create or reuse the approved IIS objects.

## Package contents

- `Install-QR-IIS.ps1` — first install / full IIS prerequisite and deployment path.
- `Update-QR-IIS.ps1` — controlled update of an existing DA Secure IIS deployment.
- `Rollback-QR-IIS.ps1` — explicit rollback to the latest or a selected deployment backup.
- `QR-IIS.Common.ps1` — shared safety/deployment engine used by the three entry scripts.
- `README.md` — this runbook.
- `BUILD-MANIFEST.json` — source/build provenance and SHA-256 payload hash.
- `publish\` — framework-dependent `dotnet publish` payload generated by CI.

## Persistence guarantees

The deployment engine explicitly excludes `App_Data` from both backup mirroring and deployment mirroring. It never uses `Remove-Item` against `App_Data`.

The following live data therefore stays in place across install, update and rollback:

- `App_Data\keys` Data Protection keys.
- SQLite database files under `App_Data`.
- `App_Data\backups` application backups.
- Other runtime files already located under `App_Data`.

Before replacing an existing payload, the scripts stop AppPool `QR` and copy the current application payload to `C:\inetpub\wwwroot\QR_deployment_backups\deploy-<timestamp>`, excluding `App_Data`. Existing `appsettings*.json`, `.env`, `appsettings.Local.json`, and `appsettings.Secrets.json` are overlaid onto the staging payload so production configuration is not replaced by package defaults.

Deployment staging occurs under `%ProgramData%\DA-Secure\staging`, outside the IIS wwwroot.

## Firebase credentials

The server implementation supports either `Firebase:CredentialPath` or Google Application Default Credentials. These scripts expose both approved deployment forms without copying credentials into wwwroot.

### Option A — Firebase:CredentialPath

Place the service-account JSON in a protected location outside `C:\inetpub\wwwroot\QR`, for example:

```powershell
C:\ProgramData\DA-Secure\firebase\service-account.json
```

Then run:

```powershell
.\Install-QR-IIS.ps1 `
  -FirebaseCredentialPath 'C:\ProgramData\DA-Secure\firebase\service-account.json' `
  -ConfigureHostsFile
```

The script stores the path in the AppPool environment as `Firebase__CredentialPath`, which ASP.NET Core maps to `Firebase:CredentialPath`.

### Option B — GOOGLE_APPLICATION_CREDENTIALS

```powershell
.\Install-QR-IIS.ps1 `
  -GoogleApplicationCredentials 'C:\ProgramData\DA-Secure\firebase\service-account.json' `
  -ConfigureHostsFile
```

The credential file must exist and must be outside the IIS deployment root. Do not put it in the repository, this package, `publish`, or `wwwroot`. Credential contents are never written to deployment logs.

If either credential parameter is supplied, deployment automatically requires Firebase health to become `READY`. `-RequireFirebaseReady` can also be used when the credential is already configured on the server and should be enforced during deployment.

## First installation

Open **Windows PowerShell as Administrator**, extract the package, then:

```powershell
Set-ExecutionPolicy -Scope Process Bypass -Force
Set-Location <extracted-package-path>
.\Install-QR-IIS.ps1 -ConfigureHostsFile
```

The installer:

1. Requires elevation.
2. Enables required IIS features and IIS management scripting support.
3. Detects .NET 10 ASP.NET Core runtime + AspNetCoreModuleV2.
4. Downloads/installs the .NET 10 Hosting Bundle only when required.
5. Creates/reuses AppPool `QR` as a No Managed Code integrated pool.
6. Creates/reuses site `API` at `C:\inetpub\wwwroot\QR`.
7. Finds a non-expired `*.da.gov.kw`/`testapi.da.gov.kw` certificate in `LocalMachine\My` with a private key.
8. Configures the SNI HTTPS binding on port 443 and removes the temporary HTTP host binding.
9. Optionally backs up and updates the hosts file to `127.0.0.1 testapi.da.gov.kw`.
10. Applies read/execute permission to the application payload and modify permission only to `App_Data` for `IIS AppPool\QR`.
11. Deploys the staged publish payload while excluding `App_Data`.
12. Starts the AppPool and polls `/health`.
13. Reports application version plus Firebase `status/detailCode`.
14. Automatically restores the previous payload when startup/health fails and a pre-deployment backup exists.

On a first install with no previous payload, a failed health check stops the application pool instead of pretending deployment succeeded.

## Updating

```powershell
.\Update-QR-IIS.ps1
```

With an external Firebase credential and local hosts override:

```powershell
.\Update-QR-IIS.ps1 `
  -FirebaseCredentialPath 'C:\ProgramData\DA-Secure\firebase\service-account.json' `
  -ConfigureHostsFile
```

`Update-QR-IIS.ps1` requires the existing `API` site, `QR` AppPool and .NET 10 Hosting Bundle. Use `Install-QR-IIS.ps1` if prerequisites must be repaired.

## Rollback

Rollback to the latest normal deployment backup:

```powershell
.\Rollback-QR-IIS.ps1
```

Rollback to a specific backup:

```powershell
.\Rollback-QR-IIS.ps1 -BackupPath 'C:\inetpub\wwwroot\QR_deployment_backups\deploy-20260826-001500'
```

Rollback only accepts sources inside the configured backup root. It first captures the current payload as a `pre-rollback-*` safety snapshot, then restores the selected application payload while excluding `App_Data`, reapplies permissions, starts AppPool `QR`, and validates `/health`.

## Health and Firebase status

The current application `/health` contract returns an application `status`, application `version`, and `pushProvider` object. The scripts require application `status` to be `ok` and report:

- `pushProvider.status`
- `pushProvider.detailCode`

Use `-RequireFirebaseReady` to turn any Firebase state other than `READY` into a deployment failure/rollback condition.

TLS certificate validation is not bypassed by these scripts.

## ASP.NET Core stdout diagnostics

Stdout logging is **disabled by default**. To temporarily enable it for a deployment/update:

```powershell
.\Update-QR-IIS.ps1 -EnableStdoutLog
```

The publish `web.config` is updated in staging to write stdout diagnostics under `App_Data\logs\stdout`, preserving the same App_Data persistence/permissions policy. Run the next update without `-EnableStdoutLog` to disable stdout logging again.

Do not leave stdout logging enabled longer than required for diagnostics.

## Backup retention

The scripts never automatically delete deployment backups or `App_Data\backups`. Retention/archival is an explicit operator responsibility.

## Validation scope

CI performs:

- Windows PowerShell AST/parser validation for every package `.ps1` file.
- Static persistence and credential-safety policy checks.
- `.NET 10` restore/publish.
- Service-account JSON exclusion check on the publish output.
- SHA-256 calculation for `publish\SecureQrPortal.dll`.
- GitHub Actions artifact upload of the full IIS package.

CI cannot emulate the target machine's installed `*.da.gov.kw` private-key certificate, IIS metabase, production filesystem ACL inheritance, or Firebase service-account credential. Those machine-specific checks are intentionally performed by the elevated installer itself.
